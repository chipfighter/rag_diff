## 1. 核心定位 (The Vision)

**”RAG 领域的 pytest” —— 从测试仪到调试器**

RAG-Diff 专注于解决 RAG 迭代过程中的”黑盒恐惧症”与”高昂的测试成本”。通过记录行为快照、冻结评测标准、缓存评测结果，并提供代码级的对比追踪，帮助开发者极低成本地回答三个核心问题：

1. 我这次改动，把系统改坏了吗？(Regression Test)
2. 到底是检索变差了，还是模型变笨了？(Heuristic Triage)
3. 烂在哪了？给我看看前后的具体文本。(Context Diff)

### 1.1 差异化定位 (Competitive Differentiation)

| 现有工具            | 做什么                          | 不做什么                                |
|---------------------|--------------------------------|-----------------------------------------|
| Ragas / DeepEval    | 给出评分 (Faithfulness 0.82)    | 不告诉你”和上次比哪里退化了”             |
| Arize Phoenix       | 生产环境 Trace 可观测           | 不提供开发期快速回归对比                  |
| LangSmith           | 全链路追踪                      | 重运维、SaaS 绑定、不够轻量              |
| promptfoo           | Prompt A/B 评测                 | 不聚焦 RAG 检索 vs 生成分诊              |

RAG-Diff 填补的是 **”开发者迭代循环中的快速回归检测 + 根因定位”** 这个空位。

## 2. 核心系统架构 (Core Architecture)

### 2.1 极简适配器契约 (Stupid Simple Adapter)

采用”平滑降级”的设计理念，不强制要求用户修改现有业务代码的返回值。系统通过内部的自动 **SHA-256** Hashing 实现上下文追踪（相比 MD5 避免碰撞风险且通过安全审计）。

Python

```
# 核心契约：能跑通就行，支持纯文本降级
async def ask_rag(query: str) -> dict:
    return {
        “answer”: “...”,
        “contexts”: [“文本1”, “文本2”] # 系统底层自动计算 SHA-256 Hash 并生成虚拟 ID 进行追踪
    }

# 推荐写法（结构化数据）：
async def ask_rag(query: str) -> dict:
    return {
        “answer”: “...”,
        “contexts”: [{“id”: “doc_12_chunk_1”, “text”: “...”, “score”: 0.88}],
        “route_path”: [“policy_db”] # [预留/非强制] 路由标签
    }
```

### 2.2 评测缓存引擎 (Judge Cache) - **P0 级核心**

为彻底解决 LLM 评测带来的 Token 成本和时间消耗，MVP 内置强制缓存机制。

- **Cache Key**: `SHA-256(Query + Answer + 排序后的 Context Hashes)`
- **命中逻辑**: 只要对应 Case 的输入和输出状态没有发生变化，直接复用上一次 (`compare-to` 目标) 的 Judge 结果。未命中才调用 Judge LLM。

### 2.2.1 多维度评测 (Multi-Dimension Judging)

MVP 内置两个核心评测维度，避免单一维度漏检：

- **Faithfulness（忠实度）**: Answer 是否基于给定的 Contexts，检测幻觉。
- **Answer Relevancy（相关性）**: Answer 是否真正回答了 Query，检测跑题/拒答。

### 2.2.2 测试集格式 (Test Set Schema)

支持可选的 `expected_answer` 字段，有 Golden Answer 时 Judge 准确度大幅提升：

```json
[
  {"query": "节假日加班费怎么算？"},
  {"query": "年假天数怎么定？", "expected_answer": "根据工龄，5/10/15天", "metadata": {"category": "hr"}}
]
```

### 2.3 版本冻结与状态隔离 (State Isolation)

抛弃传统的“覆盖式 Baseline”，采用类似 Git 的快照隔离：

- **Judge 版本锁定**: 硬编码 `JUDGE_PROMPT_VERSION = "v1.0"`，防范评测标准漂移。
- **隔离空间**: 每次 Run 生成独立的 UUID 目录。

### 2.4 根因启发式分诊 (Heuristic Triage)

当发现评测退化时，自动进行二分类诊断：

- 🔍 **疑似检索退化 (Suspected Retrieval Issue)**: Judge 判定变差，且本次的 Contexts IDs/Hashes 与基线发生改变。
- 🧠 **疑似模型退化 (Suspected Model Issue)**: Judge 判定变差，但 Contexts 列表与基线完全一致。

## 3. 开发者体验设计 (Killer DX)

### 3.1 CLI 命令路由

实现真正的开发者人体工程学，支持”时光机”与”精准爆破”。

Bash

```
# 0. 初始化项目 (生成 .ragdiff/ + 示例 testset + 示例 adapter)
$ rag-diff init

# 1. 基础运行 (默认对比 HEAD)
$ rag-diff run --testset test.json --target adapter:ask

# 2. 精确对比 (时光机模式)
$ rag-diff run --compare-to run_20260410_1000_UUID

# 3. 高效 Debug 模式 (只跑退化 Case)
$ rag-diff run --regressions-only

# 4. 极简 SRE 与成本控制
$ rag-diff run --concurrency 5 --sample 20
```

### 3.2 终端输出与 SRE 监控 (Terminal UI)

结合极简的性能监控（Latency & Token），在终端直接暴露核心问题。

Plaintext

```
🔴 [Regression] Q12: 节假日加班费怎么算？
[Triage]: 🔍 疑似检索退化 (Suspected Retrieval Issue)

--- [Metrics Diff] ---
Latency: 1.2s -> 3.5s 🔴 (+191%)
Tokens:  1024 -> 4500 🔴 (Cost Alert)

--- [Judge Diff] ---
Previous (v1.0): ✅ Grounded
Current  (v1.0): ❌ Has Unsupported Claims 
Reason: Answer 提到了"3倍工资"，但新的 Contexts 缺少相关规定。

--- [Contexts Diff] ---
- [LOST] id: hr_policy_v1_chunk_42 (或对应的纯文本 Hash)
+ [NEW]  id: faq_leave_chunk_5     

💡 开发者指引: 建议使用 --dump 命令导出完整快照进行 IDE 差异比对。
```

### 3.3 拥抱 IDE 的现场转储 (JSON Dump)

放弃复杂的 HTML 渲染，直接输出结构化现场，方便开发者使用 VSCode / Cursor 自带的 Diff 工具排查长文本。

Bash

```
# 精确执行单 Case 并导出上下文快照
$ rag-diff run -k "Q12" --dump

# 产物： .ragdiff/dumps/Q12_diff_20260410.json
```

## 附录：演进路线图 (Future Roadmap)

以下功能已明确在 MVP (v0.1) 阶段被剔除，以确保核心体验的快速落地，将作为未来版本的迭代方向：

### Phase 2: 可观测性与体验升级 (SRE & UX Plus)

- **Agentic Route Diff (路由追踪)**: 读取 Adapter 中可选的 `route_path` 字段。当检索与生成均无异常但结果退化时，诊断为 `[Triage]: 🔀 疑似路由退化 (Suspected Routing Issue)`。
- **HTML Report Exporter**: 提供 `--export-html` 命令，生成类似 GitHub 的左右分栏高亮页面，针对超长上下文 (200K+) 提供更直观的阅读体验。

### Phase 3: 评测器解耦 (Judge Decoupling)

- **自定义 Judge 注入**: 允许开发者绕过内置的云端大模型 API 评测，通过注册本地的评测函数 (如基于本地部署的 Llama-3-8B 专有评测模型) 来进行打分，满足敏感数据的本地化合规需求。
- **多维失败分类 (Failure Classification)**: 从单一的“幻觉/拒答”扩展到语气违规、格式错误、内容冗余等更细粒度的维度的 Triage 诊断。
